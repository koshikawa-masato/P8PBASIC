# 近似・特例の棚卸し（2026-11-19）

P8PBASIC の実装にある近似・部分実装・環境依存を全て洗い出し、
処遇を決めた記録。処遇は3種:

- **G（一般化）**: ハードウェア／仕様として正しく実装し直す。次期作業。
- **D（文書化した近似）**: 根拠を明記した上で近似のまま維持する。
  黙って置かないことが目的で、壊れたらここを見て判断する。
- **V（検証不足）**: 実装は実コード中継などで正しいはずだが、
  検証が届いていない。検証スイート側の課題。

## G: 一般化する

1. **ホストCLIにディスク実体化が無い**【2026-11-19 解決】
   埋め込みエンジンの実体化を src/materialize.c に切り出して共有
   化した。ホストCLI（build-host.sh が -DP8_HOST_MATERIALIZE で
   ビルドする src/main.c）は `P8P_DISK` 指定時、エンジンと同じ
   scratch へ実体化してから走る: プログラム引数があればその
   ファイルを自ディレクトリから（絶対パスで）読み、ゲストの
   ファイルアクセスは scratch 側で解決する。引数が無ければ
   ディスクのブートプログラム（MENU 優先）が起動する。
   `P8P_DISK` 無しでは従来どおり実ファイルのみで動く。DOS /
   Windows ターゲットはマクロ無しでビルドされ影響を受けない。
   検証: 素のフォルダ＋PROBE2 が Tier A 値で完走、空フォルダから
   の無引数ブートでゲームが起動継続、回帰スイート（抽出回避策を
   撤去済み）全段パス。なお RetroDOS アプリ側ツリーへは次回同期
   時に src/materialize.c の追加が必要。

2. **ディスクサブシステムの書き込みコマンド**【2026-11-19 解決】
   cmd 0x01 のデータ相をバッファし、完了時に読み取りと同じ
   セクタ走査（16 の次は次トラックの 1）で D88 イメージへ
   書き戻す実装にした。書き戻し先はメモリ上のイメージのみで、
   ディスクファイル自体は変更しない（器はファイルを "rb" で
   一括読みして閉じる）。つまり書き込みはセッション内では
   実フロッピー同様に全リーダー（サブシステム／ファイル層／
   XDE サービス）から見えるが、ユーザーの .D88 は守られる。
   検証: tools/subsys_test.c（PUTCOM/PUTDAT 経由の書き込み→
   サブシステム読み戻し＋ファイル層読みの一致、セクタ16→
   次トラックのラップ、ファイル無変更の確認）。NEOMSC は
   書き込みを使わないため MA2026 の動作は従来どおり。

3. **ポート 0x31 bit1（64RAM ウィンドウ）**【2026-11-19 解決】
   0x8000–0x83FF は通常、ポート 0x70 で基底を決める 1KB の
   RAM ウィンドウ（OUT 0x70 = 値<<8、IN 0x70 で読み戻し）で、
   ポート 0x31 の bit1（64K RAM）または bit2（N）が立つと
   恒等マッピングになる（QUASI88 の
   main_memory_mapping_8000_83ff の意味論）。src/vessel.c の
   Z80 バス（mem_read / mem_write）に実装した。基底の初期値は
   0x8000（恒等）で、起動済み BASIC が残す状態に合わせたため、
   ゲストがポート 0x70 / 0x31 を触らない限り従来動作と一致
   する。器自身のサービス（XDE のネイティブ転送等）は DMA
   相当としてフラットアドレスのまま。検証:
   tools/window_test.c（Z80 ルーチン経由の読み書き 11 件）。
   NEOMSC は CG 展開と OPNA バーストの前後でトグルするが、
   RD=1 構成の MA2026 では従来どおり実害なし（回帰スイートで
   再確認）。

4. **ゲストテキストイメージ（0xF3C8）の表示合成**【2026-11-19 解決】
   実機では 0xF3C8 はテキスト VRAM そのものだが、埋め込み
   エンジンはインタプリタ自身の画面（halp8 の tv/ta）とゲスト
   イメージの二面持ちだったため、イメージだけに描くものが
   アプリで見えなかった: FFDE サービス3のスタッフロ―ル全文と、
   BASIC 本体が TXR=&HF418（イメージの属性面）へ POKE する
   選択カーソル／再生中マーカーの属性。
   解決: src/engine.c の p8_text_codes / p8_text_attrs が二面を
   合成して返す（p8_frame のグラフィック合成と同じ方針）。
   イメージのコードが勝ち（空白 0x20 は素通し、漢字は SJIS
   ペア→インタプリタの JIS パック形式へ変換）、属性は CRTC
   トランスペアレント形式の（桁，属性）ペア列を QUASI88 の
   crtcdmac と同じ意味論でデコードする: 色コマンド（bit3）は
   色＋セミグラフィックを指定し装飾を保持、装飾コマンドは
   色とセミグラフィックを保持する（カラー属性モード）。
   属性ペアはインタプリタのセルも再色付けする（ただしセルの
   色を実際に変える場合のみ。リストの緑／シアンの列と
   マーカーがこれで効く）。検証: tools/textmerge_test.c
   （単体 18 件）とスイートの embed text 段（*SELECT 画面）。
   残る既知の差: (a) インタプリタの CLS はゲストイメージを
   消さないため、属性ペアを再構築しない行では古いイメージが
   勝ち得る（MA2026 は画面ごとにペアを再構築するので無事）。
   (b) セミグラフィックのドット描画はホスト側の仕事: エンジンは
   セルと属性 bit4（グラフィック）を渡すが、RetroDOS の
   P8Bridge はまだ文字グリフで描く。(c) 点滅は位相を持たず
   常時表示、反転は属性バイトに載せていない。

5. **DOS ビルド（build.sh / build.bat）**【2026-11-19 決定・対処済】
   P9PBASIC 由来のターゲットで、P9PBASIC.EXE（PC-98 MS-DOS）を
   作るスクリプトがフォークに未適応のまま残っていた。器への
   参照は fileio.c の BLOAD,R だけでなく exec.c 全体（XDE/XDD/
   XDF リレー、文ループの vessel_statement）に及ぶため「フックだけ
   外す」ことはできず、器なしの DOS 版は XDE 系が無言で無効な
   インタプリタになる。16ビットラージモデルに器＋ymfm（C++）＋
   D88 層を載せる現実性も無い。決定: DOS は P8PBASIC の
   ターゲットとしない。build.sh / build.bat は冒頭で理由と
   代替（build-host.sh / build-embed.sh）を明示して停止する
   ようにした（リンク段階の不可解な失敗を排除）。スクリプト
   自体は上流との差分を最小化するため残置する。P8 の現行
   ターゲットはホストCLIと埋め込みエンジン。

## D: 文書化した近似（維持）

6. **文単位ポンプ**（src/vessel.c STMT_CYCLES = 2,000 サイクル、
   vessel_statement）【2026-11-21 改訂】
   BASIC の exec_loop 1周ごとに、基本量として固定量のエミュレーション時間を進める。
   実機では文の実行時間は内容で変わるため、これは時間の近似。
   サイクル精度の解釈実行は目標にしない（DESIGN の範囲外）。
   - **量**: 1文 = 2,000 サイクル（4 MHz で約 0.5 ms）。実機 ROM の
     単純な文（PRINT / LOCATE / READ / POKE / NEXT の混在）は
     およそ 500〜4,000 サイクルで、その中ほどを取った値。長い
     PRINT だけが旧来の課金量に近づく。したがって PRINT の多い
     プログラムは実機よりやや速く、空の遅延ループはやや遅く
     進む（許容する近似）。
   - **数える単位**: exec_loop の1周ごと。文だけでなく、文区切りの
     「:」と行の繰り上がりも1周として同じ量を進める（従来から
     同じ。`FOR I=0 TO 2400:NEXT` は1反復 = 2周 = 4,000 サイクル）。
   - **改訂の理由**: 2026-11-21 までは1文ごとに PUMP_SLICE
     （16,667 サイクル = 4.17 ms）を丸ごと進めていた。hal_poll が
     音声リードを実時間に合わせて抑えるので、埋め込みエンジンでは
     どの文も内容に関係なく実時間 4.17 ms かかっていた。実測:
     MA2026 の曲リスト表示（menu.BAS 1070〜1550 行、約 2,400 周）が
     器で 10.1 秒、実機はおよそ 1〜3 秒（文コストからの推定）。改訂後の見込みは約 1.2 秒
     （2,400 × 0.5 ms）。プログラムが書いた遅延ループも同じ倍率
     （約 8.3 倍）で引き延ばされていた。
   - **変えていないもの**: PUMP_SLICE（16,667）は vessel_pump() の
     1回分として残り、1文の内側でまとめて経過する時間、すなわち
     セクタ待ち（vessel_burn、項目 8 の XDE_SECTOR_CYCLES）と
     実行ループの hal_poll 間隔（run_poll）が使う。ディスク／DRAM
     転送のペーシング（ADPCM の DRAM 転送 約19秒）は別系統で、
     この改訂の影響を受けない。割り込みの配送ループ（最大2回）も
     同じ。
   - 機械語呼び出し（vessel_call）やセクタ待ちを含む文は、その
     実サイクル／待ち時間に加えて 2,000 サイクルが乗る（文の
     ディスパッチ分に相当。二重計上ではない）。INP / OUT と
     hal_idle は時間を進めない。
   検証済み（2026-11-21、メンテナ）: 実測で DRAM 転送開始→1曲目
   発音が 36.2 秒 → 27.2 秒に短縮（曲リスト相は約 1.2 秒、見込み
   どおり）。55 秒 embed の音声フェーズは BGM 1〜22 秒／無音
   23〜28 秒／1曲目 29 秒〜で、wavprofile の窓を再導出した。
   フルスイート PASSED。時間依存の基準は再導出済み: PROBE4 は
   新モデルで決定的（3回一致）なため再 bless（サンプル間隔の
   エミュレーション時間が変わり、&HFFFF の減分が約 −103/回に
   なったもの）、PROBE46 は固定ループ待ちをイベント待ち
   （&HAA21 のループフラグをポーリング、上限付き）に変更して
   基準値は不変、embed55 カウンタは再ピン留め（tb_irqs
   3320→4366 他: 遷移の遅れが消えて audio 50 秒時点で先の曲まで
   進むため）。QUASI88 差分確認の取り直しは未実施。

7. **hal_poll のペーシング**（src/halp8.c、64文ごと）
   埋め込みHALが音声リードを見て眠る間隔。ホストHAL では無効
   （オフライン最速）。近似ではなくホスト側の実行制御。
   1回の確認間隔が進めるエミュレーション時間は、文ループでは
   64 × 2,000 サイクル = 約 0.03 秒（項目 6 の改訂前は約 0.27 秒）、
   セクタ待ち／実行ループ経由では従来どおり 64 × PUMP_SLICE =
   約 0.27 秒。どちらも 2秒リングが吸収できる範囲。halp8.c 内の
   コメントは旧値（1文 ≒ 4 ms、0.27 秒）のままで、文ループに
   ついては古い。

8. **XDE 転送時間**（src/vessel.c XDE_SECTOR_CYCLES = 133,333）
   約30セクタ/秒。QUASI88 の実測（約35ms/セクタ）で校正した値。
   実機のシーク時間まではモデル化しない。

9. **SOUND 文はビーパー近似**（src/exec.c、P9PBASIC 由来）
   MA2026 は使わない。PC-88 の SOUND は音源ボード前提で、
   器の OPNA へ写すのが正道だが、需要が実証されるまで近似で維持。

10. **ADPCM-A 固定リズムROMは分離点のみ**（docs/DESIGN.md §音楽再生）
   MA2026 同梱 PMD はサンプルRAM駆動で固定レイアウトを使わない
   ことを実測済み。他タイトルで必要になったら供給部を実装する。

11. **VRTC ハンドラのチェーン先 0xE808 は EI;RET スタブ**
    実機では BASIC ROM のハンドラへチェーンする。器には ROM が
    無いためスタブで受ける。PMD のフェード／効果音処理は器側で
    完結しており、MA2026 の挙動に差は出ていない（実測）。

15. **FFDE サービス1のロード先は ADPCM-B DRAM**（src/vessel.c
    vessel_dram_load、src/opna_ymfm.cpp）【2026-11-20 訂正・H-2】
    サービス1のネイティブ代行は PCM データブロックを YM2608 の
    ADPCM-B DRAM（256KB、オフセット0から）へ直接書く。実機の
    NEOMSC はバンク1レジスタ経由のバースト書き込みで同じ DRAM を
    埋める（転送時間は項目8で近似）。PMD の PCM パートはバンク1
    （制御 reg 00H、delta-N）= ADPCM-B で再生する。以前は誤って
    ADPCM-A 側へ書いており、MA2026 の実測ではデータは一度も
    読まれていなかった。
    リズム音源（ADPCM-A）はチップ内 ROM で、ホスト側の別供給が
    前提（項目10）。未供給の間は常にゼロを読み出す。
    回帰テスト: tools/dramload_test.c。

16. **漢字ROMポート E8–EF と代替フォント**（src/vessel.c、
    src/kanjifont.c）【2026-11-20】
    ゲスト（NEOMSC/XDD）は日本語テキストをグラフィック面へ
    描く際、漢字ROMポート経由でグリフを読む。未実装の間は
    読み値が 0xFF になり、16×16 の塗りつぶしになっていた。
    実装: OUT E8/E9 = ROM1 アドレスラッチ（下位/上位）、
    EC/ED = ROM2、EA/EB は受理して無視（実測では EA は常に
    E9 と同値、EB は常に 0x80）。IN E9 = グリフ左半分、
    IN E8 = 右半分（行はアドレス下位ニブル、ゲストが行ごとに
    再ラッチ）。アドレス配置は QUASI88 の kanji2addr（公開
    されたハードウェア挙動記述）に従うビット詰め配置で、
    バンク0=非漢字+第1水準、バンク1=第2水準。
    1バイト文字（JIS X 0201）は実ROM同様のフラット配置:
    コード C のグリフはストリームオフセット C×16 の16バイト
    （ストリーム = テーブルを [index][行×2+半分] 順に平坦化
    したもの）。XDD のテキストプロッタは addr = C×8 をラッチし
    (E9,E8) ペアで8回読む = グリフの16行そのもの。QUASI88 の
    ステータス描画も同じ読み方をする（&kanji_rom[0][c * 8][0]
    から1バイト/行で16行）。当初 index=コード に置いたところ
    XDD が描く ASCII 文字列（MA2026 の
    "Presented by MEGAFEPPS,2026"）が文字化けしたため、
    2026-11-20 にフラット配置へ訂正（実機報告で発覚、
    ハーネスで修正確認済み）。
    フォント実体は NEC ROM の流用ではなく、パブリック
    ドメインの東雲フォント（しののめ、JIS X 0208 16×16 と
    JIS X 0201 8×16）から生成した代替フォント
    （tools/gen_kanjifont.py）。NEC の ANK 特殊記号とは一部
    字形が異なる（状態表示行の記号類のみ、本文は問題なし）。
    回帰テスト: tools/kanjifont_test.c（トレース実測の配置を固定）。

23. **HALT は割り込み待ち、実行はステップ上限つき**（src/vessel.c
    halt_wait / HALT_WAIT_CAP、run_loop_body / STEP_CAP）
    【2026-11-21、レビュー指摘 M-4】
    従来、器は HALT を実行した時点でその機械語呼び出しを打ち切り
    BASIC へ戻していた。現在は実機どおり割り込み待ちとして扱う:
    停止中の NOP を1命令ずつ回す代わりに、エミュレーション時間を
    次のタイマ事象（VRTC の 66,667 サイクル周期、Timer B が動作中
    なら tb_left の残り）まで一気に進め、通常実行と同じ
    irq_advance / irq_service を通す（音声レンダリングも同じ時計で
    進む）。進める量は停止中 NOP の粒度に合わせて 4 ステートへ
    切り上げる。割り込みがキューに入れば次の z80_step が受理し、
    ハンドラの復帰後に HALT の次の命令から続行する。
    近似と上限:
    - HALT が終わらないと判断して呼び出しを打ち切る条件は2つ。
      (a) 割り込み禁止（DI）のままの HALT。器に NMI 源は無いので
      即座に打ち切る。(b) 割り込み許可でも HALT_WAIT_CAP =
      4,000,000 サイクル（エミュレーション時間で1秒 = VRTC 60回分）
      待って配送可能な割り込みが来ない場合（ポート E4 のレベル
      不足、マスク、Timer B 停止、ハンドラ未登録）。実機なら
      止まったままになる状況で、器はホストを守るため BASIC へ
      戻す（stderr に "VESSEL HALT ... no deliverable interrupt"）。
    - 器が持つ割り込み源は VRTC と OPNA Timer B だけなので、
      それ以外（RTC、SIO、Timer A 等）で起きる前提の HALT は
      VRTC か Timer B で起きるか、上記 (b) で打ち切られる。
    - 1回の機械語呼び出し全体には従来どおり STEP_CAP = 4,000,000
      命令の上限があり、超えると "VESSEL step cap reached" を出して
      BASIC へ戻る。HALT の待ち時間は命令数に数えない（待ち1回は
      1秒で頭打ち、起床後の命令は通常どおり数える）。実機には
      無い上限で、ホストを無限ループから守るための安全弁。
    - 早送りした停止サイクルの分、Z80 コアが1ステップごとに行う
      リフレッシュレジスタ（R）の加算は行わない。長い HALT の後に
      LD A,R を読むと実機とは違う R が見える（許容する副次的な
      近似。R を乱数源にするゲストでは系列が実機と変わる）。
    - 停止中の時間は1回の機械語呼び出しの中で進むため、
      exec_loop の文ごとの hal_poll は通らない。セクタ待ち
      （vessel_burn）と同じ仕組みで、停止時間 PUMP_SLICE（16,667
      サイクル）ごとに hal_poll を呼ぶ（呼び出しをまたいで積算する
      ので、ハンドラが生きている EI;HALT の繰り返しでも効く）。
      組み込みエンジンはここで音声時計に合わせてペースを取り、
      停止／一時停止の要求もここで受け付ける。
    MA2026 への影響: NEOMSC 内の HALT（0x9E40 / 0x9E49）はディスク
    サブ CPU へ転送して実行されるコードで、メイン Z80 では実行
    されない。したがって既存の挙動・回帰値は変わらない想定
    （この変更時点ではサンドボックスでビルド／スイートを実行
    できておらず、未検証）。HALT 経路そのものの回帰テストは無い。

24. **割り込みマスク: ポート 0xE6 と 0x32 bit7**（src/vessel.c）
    【2026-11-21、レビュー指摘 M-1】
    ポート 0xE6 への書き込みは従来捨てていた。QUASI88
    pc88main.cpp の case 0xe6 に合わせて実装: bit1（VSYNC）が
    落ちている間は VRTC 要求をラッチせず、落とした時点でラッチ
    済みの要求も捨てる（延期ではなく破棄）。bit0（RTC）/ bit2
    （SIO）は器に割り込み源が無いため保持するだけ。
    **サウンド割り込みは 0xE6 に含まれない**: QUASI88 では
    0xE6 が扱うのは SIO / VSYNC / RTC の3ビットだけで、サウンドの
    マスクはポート 0x32 の bit7（SINTM、1=禁止。44H 系ボード）と
    ポート 0xAA の bit7（A8H 系ボード）。docs/NEOMSC-CONTRACT.md の
    旧記述「0xE6 の 0x80=SOUND」は誤りで訂正した。NEOMSC は
    0xE6 に 2 しか書かず（OUT は 0x9EE8 と 0xA4BF の2箇所）、bit7 を
    立て直す書き込みは無いので、bit7 をサウンド許可として実装
    すると最初の CG 展開以降シーケンサ割り込みが永久に止まる。
    0x32 bit7 は実装した。QUASI88 と同じく、SINTM は割り込み
    コントローラの**手前**でチップの要求レベルをマスクし、
    コントローラは「Timer B フラグが立っている かつ IRQ 許可
    （reg 0x27 bit3）かつ SINTM が落ちている」の立ち上がりエッジを
    ラッチする（tb_line_update の tb_line）。ラインは入力が変わる
    全ての箇所（オーバーフロー、reg 0x27 書き込み、0x32 書き込み）で
    追跡する。irq_advance ごとの標本化だけだと、確認応答と次の
    オーバーフローが同じ標本間隔に入ったときエッジを取りこぼす。したがって SINTM 中の
    オーバーフローは、ゲストがチップ側でフラグを確認応答
    （reg 0x27 bit5）してからマスクを外せば割り込みにならず、
    フラグを残したまま外せばその時点でエッジになる。逆に、
    0xE4 のレベル不足で配送待ちになっているラッチ済みの要求は、
    後から SINTM を立てても消えない（配送側は SINTM を見ない）。
    フラグを確認応答しないゲストには次のエッジが来ない（実機と
    同じ）。bit5（パレット）/ bit6（EVRAM）の扱いは不変。
    既定値はどちらも「マスクなし」（0xE6 = 0xFF 相当、0x32 = 0x20）
    で、ゲストが書くまで従来動作と同じ。実機のリセット値
    （QUASI88 では VSYNC 禁止で始まり ROM が許可する）は再現
    しない。0xAA はバンク1アドレスの別名のまま（項目 20 の
    既知の競合）で、マスクとしては未実装。
    MA2026 への影響: NEOMSC の 0x32 アクセスは bit6 の RMW のみ、
    0xE6 は VSYNC を許可したままの 2 だけなので、配送は変わらない
    想定（未検証、項目 23 と同じ事情）。同梱 PMD のバイナリが
    0x32 bit7 を立てるかどうかは未確認。

25. **NEOMSC／PMD 固有の代行は NEOMSC 検出時だけ有効**（src/vessel.c
    neomsc_loaded / vessel_notify_load / vessel_relay_target、
    src/exec.c stmt_ext）【2026-11-21、レビュー指摘 T-1】
    従来は NEOMSC にしか当てはまらない代行が無条件に効いており、
    別タイトルやユーザー自作の機械語が黙って誤動作した。
    - **検出述語**: 「ロード通知（vessel_notify_load）の範囲が
      NEOMSC の BSAVE ヘッダ範囲 0x9900–0xA95E（0x105F バイト）と
      ちょうど一致し、かつロード後のゲストメモリ 0x9900 からの
      30 バイトが署名と一致する」とき NEOMSC ありとする。この範囲を
      通知できるのは BLOAD だけ（もう一方の通知元 vessel_disk_read は
      256 バイト単位）。署名は MA2026 ディスク上の NEOMSC 本体の
      先頭 30 バイト（ファイルの 4..33 バイト目）:
      `F3 3E C3 32 A1 EE 32 A4 EE 32 A7 EE 21 4D 99 22 A5 EE
      21 5C 9E 22 A2 EE 21 DB A6 22 A8 EE`
      （DI; LD A,C3h; EEA1/EEA4/EEA7 へ JP オペコード; 0x994D /
      0x9E5C / 0xA6DB を各ベクタのオペランドへ）。フック設置の
      全体であり、3 つのハンドラ番地を絶対値で含むので、一致する
      本体は契約メモどおりの配置（0xA794 を含む）を持つ。同じ
      ベクタを使う別ドライバが一致するには、同じ長さの本体で同じ
      3 番地に同じ順でハンドラを置く必要がある。
    - **述語が見ているのは BLOAD という操作であってメモリ内容では
      ない**（近似）: 同じバイト列でも、セクタ読み（XDE サービス 0
      は 256 バイト単位の通知なので範囲が一致しない）やゲスト側の
      コピー／POKE で 0x9900 に組み立てた本体は検出されず、代行は
      有効にならない。逆方向は通知されたロードだけを追う: 本体範囲
      0x9900–0xA95E に**重なる**ロード通知のたびに述語を再評価し、
      上の条件に一致するロードなら検出、重なるが一致しないロード
      （本体の一部を置き換える BLOAD やセクタ読み）なら検出を
      解除する（本体がもう無傷でないため）。範囲に触れないロードは
      検出状態を変えない。通知を伴わない書込み（POKE、ゲストの
      機械語）による上書きは追跡しない。セッションリセット
      （vessel_session_reset）でも解除される。
    - **検出に連動する箇所**（どちらも trap()）:
      (a) PC = 0xA794 の引数フェッチ代行（DE ← (0xEC45/46)、RET）。
      (b) 0xAA00–0xAFFF の「PMD 未ロード中は RET 扱い」。
      NEOMSC 非検出時はどちらも通常のコードとして実行される。
      検出時の動作は従来と同一。
    - **検出に連動しない箇所**: RST 8 / RST 10h と ROM 番地
      （0x18A3、0x11D3、PUTCOM/PUTDAT/GETDAT、0x6F6B、0x8000 未満の
      一律スキップ）は ROM の代行なので従来どおり常時有効。XDE
      サービス 0／1 のネイティブ代行（項目 8、15）も設計どおり常時
      有効で、引数の意味と転送時間は MA2026 の実測値のまま。
    - **文中継**: XDD／XDE（サービス 0／1 以外）／XDF の飛び先は
      固定番地（0x9E5C／0x994D／0xA6DB）と先頭バイトの照合を
      やめ、EEA1／EEA4／EEA7 ベクタの JP から読む。解決条件は
      「ベクタ先頭が 0xC3、かつ飛び先が 0x8000 以上で 0xFFFF
      （器の番兵）でない」（RAM のハンドラだけを中継する方針。器は
      ROM イメージを持たず、特定の ROM 番地の代行しか無い）。
      入口レジスタは契約メモの表どおり: XDD は BC=0xEEA1、
      HL=第1引数トークン、A=そのバイト。XDF は BC=0xEEA7、
      HL=コマンド文字、A=その文字（従来は A=0、BC=0x8F00 を渡して
      いた。純正 NEOMSC は A を (HL) から読み直すので差が出な
      かったが、A で分岐する差し替えハンドラは壊れる。同日修正）。
      XDE は BC=0xEEA4、A=第1引数のトークンバイトで、**HL だけは
      実機の 0xE69C ではなく第1引数トークンの位置**を渡す（器は
      ROM 側のテキストポインタを持たず、RST 8 svc 0x2C と 0x11D3 の
      代行が HL から後続引数を読むため。意図的な乖離）。A の

18. **SCREEN 表示スイッチの訂正**（src/graph.c）【2026-11-20、
    2026-11-21 再訂正】
    第2引数 sw は 2 ビットのスイッチの組である（NEC PC-8801mkIIMR
    N88-BASIC リファレンスマニュアル SCREEN の項）: ビット値 2 =
    グラフィックマスク（ON の間グラフィックを一時的に隠す。内容は
    保持され、マスクを切ると元どおり表示される）、ビット値 1 =
    高速書き込み（表示には影響しない。V2 モードでは無意味）。
    SCREEN はテキスト面の表示には一切関与せず、テキストは常に
    表示される。したがってグラフィックの表示条件は、ディスプレイ
    ページが選択されている（dp != 0）場合に !(sw & 2):
    sw=0 テキスト+グラフィック、sw=1 テキスト+グラフィック、
    sw=2 テキストのみ（グラフィックはマスク、内容保持）、
    sw=3 テキストのみ（マスク ON）。
    訂正の根拠（2026-11-21）は上記マニュアルと MA2026 の実機相当
    録画（M88）: タイトル（SCREEN 0,0）では PRINT したヘッダ行が
    XDD グラフィックの上に表示され、演奏パネルはテキスト面の
    インジケータと共存する。*SELECT（SCREEN 0,2）はリストのみで、
    グラフィックは下に保持されている。
    ビルド 97 の旧対応（0=グラフィックのみ、1=重ね合わせ、
    2=テキストのみ）は QUASI88 の観察から導いたもので誤り:
    sw=0 でテキスト面を隠し（MA2026 のヘッダ行が出なかった原因）、
    sw=3 でグラフィックを表示していた。stmt_screen は hal_ton を
    呼ばなくなった（テキスト表示は初期化時の hal_ton(1) のまま）。
    なお、それ以前の sw=2 を「重ね合わせ」とする対応で *SELECT の
    リストの下に CG が残った点（実機報告）は、マスクとして
    引き続き解消されている。

19. **XDD のデータ参照形が何も描かない**【2026-11-20 解決】
    原因は vessel 側の中継だった: exec.c の ext_build_stream が
    引数区切りを全て ',' (0x2C) に潰していた。NEOMSC の FFDD
    ハンドラ (0x9E5C) は5番目の引数の直後のバイトで分岐する --
    ',' なら直接形 (0x9F65: 評価した記述子を文字列ポインタとして
    描画)、';' なら RST 0x10 経由でデータ参照形 (曲番号・種別を
    取得し 0xA445 の曲表を引いて DB 文字列を描画)。';' が ',' に
    潰れたためデータ参照形が直接形へ誤誘導され、曲番号 (小さな
    整数) がポインタとして解釈されて何も描かれなかった。
    修正: (1) stmt_ext が引数ごとの区切り文字を記録し、
    ext_build_stream が元の区切りを保持する。(2) vessel に
    RST 0x10 (ROM の CHRGET: A=(HL)、HL を進め空白を飛ばす)
    のトラップを追加 -- データ参照形の経路で初めて必要になった。
    検証: MA2026 アトラクトの *TITLE パネル (タイトル2行+
    コメント6行+M.Sコメント5行+クレジット) が QUASI88 の
    レイアウト (漢字ROM無しのためバー状) と同じ位置に描画され、
    パネル領域の VRAM 非ゼロバイトは 112 → 7,322 に回復。

20. **ADPCM-B (PMD の PCM パート) が鳴らない**【2026-11-20 解決】
    原因はポートマップの欠落: 同梱 PMD (v3.3) の opnset46 は
    OPNA バンク1 をポート 0xAC (アドレス) / 0xAD (データ) で
    駆動する (サウンドボードII の A8-AF デコード。QUASI88
    pc88main.cpp の case 0xac/0xad が genuine)。vessel は
    NEOMSC 自身が使う 0x46/0x47 のペアしかマップしておらず、
    PMD からの ADPCM-B レジスタ書き込みが全て無言で捨てられ、
    PCM パートのデータは進行するのに発音しなかった。合わせて
    eoscheck が読む拡張ステータス (ポート 0xAC 読み、bit2=EOS)
    も未実装で、恒常 0xFF が返っていた (bit2 が立つため当面は
    偶然ゲートを通過していたが、意味的には不正)。
    修正: vessel_port_out に 0xAC/0xAD をバンク1 として追加、
    vessel_port_in の 0xAC に ymfm の read_status_hi() を返す
    opna_status_hi() を接続。検証: 26曲目 (ADPCM使用) の再生で
    ADPCM-B レジスタ書き込み 0 → 43,012 回、キーオン (reg0=0xA0)
    769 回、ymfm の ADPCM-B メモリ読み出し 0 → 840,005 回。
    回帰ガード: tools/pcmb_ports_test.c (0xAC/0xAD のみで
    キーオンして PLAYING の成立と終了を確認)。
    EOS の観測について (Astra レビュー 2026-11-20 で判明):
    ymfm はリセット時にフラグ制御レジスタ (バンク1 reg 0x10)

    書き込みで制御するもので、マスクを外せば再生終了時に
    EOS (bit2) が正しく読める (実測 0x0C = EOS|BRDY)。
    当初「ymfm は EOS をラッチしない」と記録したのは
    マスク未解除の観測による誤りで、訂正する。
    残る既知の競合: 従来からある 0xAA/0xAB のバンク1
    エイリアスは、実機 (QUASI88) では 0xAA = サウンド
    割り込みマスク書き込みと競合する。現行コーパスで
    エイリアスを必要とするゲストは未確認のため今回は
    残置し、他タイトル展開時 (ステップ4) に再確認する。

    なくサブルーチン呼び出しに変えるトラップ。変換器はこの2文を
    出力テキストから削除する（文頭にある場合のみ。削除した結果

    黙って行っていた書き換えで、ここに近似として明記する。
    - **削除するもの**: 文 `STOP ON`（トークン 90 95）と、文
      `ON STOP GOSUB <飛び先>`（95 90 8D から文末まで）。削除の
      たびに変換レポートへ `line N: dropped STOP ON` /
      `line N: dropped ON STOP GOSUB` を出す（ホスト CLI と
      エンジンの実体化はレポートを捨てるので、見るには
      tools/p88_to_bas.py か -DP88CONV_TEST のドライバを使う）。
      `STOP OFF` / `STOP STOP` は対象外で、変換器は OFF の
      トークンを知らないため未知バイトとして報告される。
    - **理由**: インタプリタに STOP トラップが無い。そのまま通すと
      壊れる（コード読解による確認。サンドボックスで実行できず
      未実行）:
      (a) `STOP ON` は exec.c の文ディスパッチで T_STOP として
      実行され、後続トークンを見ずに do_end(1) へ入る。つまり
      その場でプログラムが「中断しました」で止まる。
      (b) `ON STOP GOSUB` は stmt_on が ON ERROR / ON KEY 以外を
      `ON <式> GOTO/GOSUB` として扱うため、T_STOP を式として
      評価しようとして Syntax error になる。
      (c) トラップ機構はファンクションキー用（keytrap_*、
      ON KEY GOSUB / KEY(n) ON）と ON ERROR だけ。STOP キーは
      exec_loop が hal_breakflag() を見て直接 do_end(1) を呼ぶ。
      (d) HAL 側: hal98.c はスキャンコード 0x60 と CTRL+C、
      halhost.c はキースクリプトの `\s` でフラグを立てる。
      埋め込みエンジンの halp8.c には brkflag を立てる経路が無く、
      STOP キー自体が存在しない。

      埋め込みエンジン（アプリ）では STOP キーが無いので何も
      起きない。

27. **OPNA の読みポートと割り込み配送**（src/vessel.c vessel_port_in /
    opn_data_read / opn_write / irq_service、src/opna_ymfm.cpp
    opna_data_hi）【2026-11-21、レビュー指摘 L-1 残り】
    1チップが 44H–47H と A8H–ADH の両デコードに応答する（実機は
    機種構成でどちらか一方。この点は従来どおりの近似）。読みは
    QUASI88（pc88main.cpp main_io_in、soundbd.cpp）のポート
    マップに合わせた:
    | ポート | 返すもの |
    |---|---|
    | 44H / A8H | ステータス: bit1 = Timer B フラグ、BUSY は常に 0。器自身のタイマーモデル（tb_flag）から返す |
    | 45H / A9H | バンク0 データ: 選択レジスタ 00H–0FH（SSG）は書いた値、FFH はボード ID、他は 0 |
    | 46H / ACH | 拡張ステータス（ymfm の read_status_hi()）: EOS bit2 / BRDY bit3 / PLAYING bit5 |
    | 47H / ADH | バンク1 データ: レジスタ 08H の ADPCM-B メモリ読み（ymfm の read_data_hi()）、他は 0 |
    - **44H/A8H を ymfm の read_status() に寄せない理由**: ラッパーは
      ymfm のタイマー（ymfm_set_timer）を実装しておらず、チップ側の
      タイマーフラグは永久に立たない。Timer B は器の割り込み
      モデル（tb_period、QUASI88 校正の 3.9936 MHz）が持つ。寄せると
      PMD のシーケンサが止まる。同じ理由で 46H/ACH の bit0–1
      （タイマーフラグ）は 0 のまま（QUASI88 は FLAG_B/FLAG_A を
      載せる）。ACH の値は build 98 から変えていない。Timer A は
      未実装。
    - **従来**: 45H/46H/47H/ADH は常に 0xFF、A9H は選択レジスタに
      関係なく 1 だった。NEOMSC の ADPCM 転送（0x9A98 の
      `IN A,(46H)` / `BIT 3,A` の BRDY 待ち、0x99ED のレジスタ 08H
      読み）はこの読みに依存するが、MA2026 では XDE サービス 0/1 を
      ネイティブ代行するのでこの経路は走らない。
    - **A9H**: プローブ（NEOMSC 初期化、PMD の boardselect、
      MENU.ALP 200 行）はどれもレジスタ FFH を選んでから読むので
      答えは従来どおり 1。PMD88 v3.7 ソース上、データポートの読みは
      boardselect の1箇所だけ（同梱 v3.3 のバイナリは未確認）。
    - **45H のボード ID（解決済み、2026-11-21 rev）**: 当初は
      PROBE24 の基準値（`p1= 255`）を守って 0xFF のまま残したが、
      その後、根拠が確定したので A9H と同じ 1 に直した。根拠:
      MENU.ALP 190 行 `OUT &H44,255:A=INP(&H45):IF A=1 THEN 240`
      が SB2 検出そのもので、レジスタ FFH 選択時の答えとして 1 を
      期待する（200 行は A8H/A9H の双子）。QUASI88 の答えも
      「44H 系に SB2 があれば 1」。器は 44H 系に SB2 として応答
      するので 1 が genuine。PROBE24.BAS 13 行はこのプローブの
      写しで、その基準値は誤答を固定していた（p1= 255 → 1 に
      再ブレス）。これで MENU.ALP は 190 行のプローブで SB2 経路に
      入り、200 行の A9H プローブは実行されなくなった。
    - **ヘッドレス（WAV もシンクも無い）時**: チップは不活性で、
      46H/ACH は固定 0x04（EOS のみ）、47H/ADH は 0。
      （ACH の 0x04 は従来どおり。46H は従来 0xFF で、今回 ACH と
      同じ値に統一された。）
      BRDY が立たないので、NEOMSC の ADPCM 転送を実コードで
      走らせると BRDY 待ちがステップ上限まで回る。
    - **配送順**: irq_service は VRTC を Timer B より先に配送する
      （実機コントローラの優先度。0xE4 の閾値 2 / 5 と同じ順）。
      従来は Timer B が先だった。両方がラッチされているときは
      VRTC を先にキューし、Timer B はラッチのまま残る。保証される
      のは「要求が失われない」ことまでで、厳密優先度ゆえ、割り込み
      禁止の間に VRTC が再ラッチし続ける状況では Timer B の配送が
      繰り返し後ろへずれうる（無期限の遅延も原理的にはありうる）。
      通常は VRTC が受理された直後の調停で Timer B が配送される。
    - **Timer B の再開位相**: reg 0x27 の LOAD B（bit1）の 0→1 で
      カウンタに周期をロードし直す（QUASI88

32. **キーボードの文字生成はマトリクスから HAL が行う**（src/halp8.c
    keyscan / ks_keycode）【2026-11-21、keyscan_test（73 件）と
    回帰スイートで検証済み】
    アプリはキーマトリクス（halp8_set_matrix）しか送らず、文字
    キュー（halp8_push_key）へは誰も積んでいなかった（embed ハーネス
    は従来から明示の文字送りとマトリクス保持を使い分ける）。
    このため INKEY$／INPUT／行エディタには何も届かなかった（INP と
    器のポート 00H–0EH はマトリクスを直接読むので動いていた）。
    実機ではキーボードのスキャン（ROM／キーボード側ファームウェア）が
    マトリクスの押下エッジを文字に変え、オートリピートを掛ける。
    埋め込み HAL がその役を代行する。
    - **駆動点**: hal_poll（64 文ごとのゲートの後）、hal_idle、
      hal_getkey。すべてインタプリタ側スレッド。マトリクスは読むだけで
      書かない（hal_keymatrix／器のポート読みは従来どおり。読むのは
      項目 34 のキーバッファを通った後のマトリクス）。走査は
      呼ばれたときだけ進むので、呼び出しの間に押して離したキーは
      取りこぼす（実機は割り込みで走査する）。
    - **配列**: QUASI88 のキーポート表（行 0–11）。表に無いセルは
      何も生成しない。
    - **生成規則**: 押下エッジ（前回スナップショットで 1、今回 0）で
      1 文字。修飾キーはその時点のマトリクスから読む。英字は大文字が
      基本で SHIFT で小文字、CAPS ロックはその向きを反転する。数字／
      記号は JIS 刻印の SHIFT 対（SHIFT+0 は無し、行 7 ビット 7 の
      キーは SHIFT 時のみ `_`）。テンキーは SHIFT に依らない。
      カーソル 1CH–1FH、HOME 0BH（SHIFT で KC_SHOME）、INS/DEL は
      7FH（SHIFT で 12H）、F1–F5 は KC_F1+n（SHIFT で KC_SF1+n）、
      HELP／COPY／ROLL UP／ROLL DOWN は KC_*。
    - **STOP／CTRL+C**: 文字は積まず brkflag を立てる（exec_loop が
      hal_breakflag で中断する）。立てるのはプログラム実行中のみで、
      ダイレクトモードのプロンプトでは実機どおり何もしない（古い
      フラグが残ると次の入力キーを食ってしまうため）。これで埋め込みエンジンにも STOP の
      入口ができたので、項目 26 (d) の「halp8.c には brkflag を立てる
      経路が無い」は古い記述になった（STOP トラップ自体は未実装の
      まま。押せばプログラムは「中断しました」で止まる）。
    - **CTRL**: 英字は 1–26。主ブロックの数字・記号は何も生成しない
      （実機の CTRL+@ = 00H、CTRL+[ = 1BH などは未モデル）。テンキー、
      SPACE、RETURN、カーソル等は CTRL を見ない。
    - **CAPS／カナはレベルで読む**: 実機では機械式ロックで、ロック
      中はマトリクスのビットが 0 のままになる。アプリの画面
      キーボードもラッチ中はセルを押し下げ続ける（Keyboard.mm の
      latched 集合）ので、スキャナは SHIFT／CTRL と同じく
      スナップショットのレベルをそのまま使う（トグル状態は持た
      ない）。INP で読むプログラムからもロック状態が見える。
    - **カナ層**: カナロック中は JIS 刻印どおりの半角カタカナ
      （JIS X 0201）。SHIFT で変わるのは数字段の小書き（ァゥェォャュョ）
      だけで、SHIFT+英字／記号の小書き・記号（ッ、ヲ、「」、。など）は
      生成せず、SHIFT なしと同じ文字になる。
    - **GRPH 層は生成しない**: GRPH を押している間は文字を一切
      生成しない（実機のグラフィック文字は未モデル）。マトリクスの
      ビットは触らないので、INP で GRPH を読むプログラムには見える。
      STOP とロックは GRPH 中も効く。
    - **オートリピート**: 最後に文字を生成したキーが押されている間、
      500 ms 後から 55 ms ごとに「最初に生成したコード」を積む（途中で
      修飾キーが変わっても再計算しない）。別のキーの押下エッジで
      対象が入れ替わり、対象を離すと他のキーが押されていても止まる。
      修飾キー・ロック・STOP は対象にならず、進行中のリピートも
      止めない。文字を生成しないキー（SHIFT+0、GRPH 中など）の押下は
      リピートを止める。時間は実時間（CLOCK_MONOTONIC）で、
      エミュレート時間ではない。500／55 ms は実機の実測ではなく
      モデル値。
    - **リピートは未読キーがある間は積まない**: キューに読まれて
      いない文字が残っている間、リピート分は保留する（最初の 1 文字は
      常に積む）。キーボードを読まないプログラムの実行中にキーを
      押し続けても、256 段のキューにリピートが何秒分も溜まって後の
      INPUT／INKEY$ に流れ込まないようにするためで、実機の
      キーバッファの挙動を写したものではない。
    - **ゴースト（ダイオード無しマトリクスの回り込み）は未モデル**:
      3 キー同時押しで 4 つ目が押されたように見える現象は、
      マトリクスにもスキャナにも入れていない。ホストが置いたビット
      だけを見る。
    - **範囲**: 埋め込み HAL（halp8.c）のみ。ホスト CLI（halhost.c）と
      PC-98 HAL（hal98.c）、キュー／p8_push_key は変えていない。
      ホストが p8_push_key で直接文字を積むこともできるが、同じキーを

    - **既存の基準への影響**: embed 段の *SELECT 遷移は RETURN の

33. **CPU クロック 4 MHz／8 MHz 切り替え**（src/vessel.c clk_mult /
    vessel_set_clock_mult、src/opna_ymfm.cpp opna_set_cpu_clock、
    src/engine.c p8_set_cpu_clock）【2026-11-22、未検証: ビルドも
    回帰スイートも未実行】
    実機（mkIIMR 世代）のクロック切り替えスイッチに当たるオプション。
    vessel の時間モデルは CPU サイクル数で数えているので、8 MHz では
    「1 秒 = 8,000,000 サイクル」として、次の原則で量を分ける。
    - **時間である量は 2 倍のサイクル数になる**（実機で秒で決まって
      いるもの）: VRTC 周期（66,667 → 133,334。CRT は 60 Hz のまま）、
      Timer B 周期（tb_period。OPNA のタイマはサウンドボード自身の
      クロックで刻むので、同じ時間が CPU サイクルでは 2 倍になる）、
      エミュレート秒の閾値（irq_advance の 4,000,000。
      P8P_COUNTERS_AT の診断スナップショットも秒のまま）、ディスクの
      セクタ時間（XDE_SECTOR_CYCLES。毎秒 30 セクタは機械の時間）、
      HALT 待ちの上限（HALT_WAIT_CAP = エミュレート時間 1 秒）。
    - **仕事である量は変えない**: 1 文の課金 STMT_CYCLES（項目 6。
      インタプリタの命令実行量であり、8 MHz では同じ仕事が半分の
      時間で済む。BASIC が速くなるのはここ）、PUMP_SLICE（時間を
      進める刻みにすぎない。8 MHz では 1 刻みが 1/480 秒になり、
      セクタ待ちの刻み数と hal_poll の回数が倍になる）、STEP_CAP
      （run_loop_body の暴走防止。z80_step の回数を数えており、
      サイクルではない）。Z80 の機械語は実行したサイクル数だけ時間が
      進むので、同じコードが半分の時間で走る。
    - **OPNA のチップクロックは変えない**（CHIP_CLOCK 7,987,200）。
      変わるのは opna_advance の「CPU サイクル → 出力フレーム」換算
      だけなので、音程とテンポは 4 MHz と同じ。ただし VRTC 割り込みや
      Timer B ではなく CPU の空ループで待つドライバは、実機と同じく
      速くなる。
    - **Timer B の位相**: 周期が pump の粒度（16,667 サイクル）より
      短い設定（レジスタ 26H が FFH に近い場合）では、irq_advance が
      1 回の呼び出しで最大 1 周期分しか戻さないため位相が失われる。
      これは 4 MHz 時代からの既存モデルで、両モード共通。PMD の
      実設定（26H = 221、周期約 40k サイクル）では発生しない。
    - **クロック判別ポートはモデル済み**: 実機はポート 6EH の bit 7 で
      クロックを読める（1 = 4 MHz、0 = 8 MHz。QUASI88 pc88main.cpp の
      IN[6E] / SW_4MHZ で照合）。vessel も同じ値を返し（FH/MH 世代の
      bit 4 = 1 を含む）、選択中のモードがソフトから正しく見える。
      VRTC を基準にループを
      数えて速度を測るソフトは実機どおりに動く。8 MHz で画面の
      ウェイトや V1 モード互換の速度調整が実機と違う点もモデルして
      いない（メモリウェイト無しの単純な 2 倍）。
    - **1 文 2,000 サイクルの近似はそのまま**: 8 MHz では 1 文
      約 0.25 ms。実機の 8 MHz はメモリウェイト等でちょうど 2 倍には
      ならないが、ここではちょうど 2 倍とする。
    - **選択はアプリがセッション単位で行う**: p8_set_cpu_clock
      （4,000,000 か 8,000,000 のみ。他の値は無視して前の値を保つ。
      既定は p8_create が置く 4,000,000）。反映は p8_start で、
      セッションリセットの前に毎回かけるので、リセットが倍率込みの
      初期値を作り、同じプロセスで 8 MHz の後に起動した 4 MHz
      セッションが 8 MHz を引き継ぐこともない。実行中のセッションの
      切り替えはできない。opna_set_cpu_clock は値が変わったときだけ
      端数（frame_acc）を捨てる。
    - **既存の基準への影響**: 既定の 4 MHz では倍率 1 で、計算される
      値はすべて従来と同一（Timer B は `… * 15000 / 13 * 1`）。
      embed ハーネスは環境変数 P8P_CLOCK（Hz）が設定されているとき
      だけ p8_set_cpu_clock を呼ぶ。ホスト CLI には切り替えを
      付けていない（常に 4 MHz）。

34. **キーバッファ（チャタリング除去）**（src/halp8.c kb_tick /
    halp8_set_matrix）【2026-11-22、同日に非対称な規則へ改訂、
    未検証: 下記参照】
    アプリのキー入力（画面上のスティック／ボタン、ゲームコントローラ）
    は、接点のばたつきや判定境界の揺れで、1 つのセルを数ミリ秒の間に
    何度も上下させることがある。従来 halp8_set_matrix はゲストが読む
    マトリクスへ直接書いていたので、ゲストはそのばたつきをすべて見た
    （メニューのカーソルが数段飛ぶ、操作が誤発火する）。実機の
    キーボードはチャタリングを除去してからマトリクスを見せるが、
    アプリからの供給は除去されていない。そこで HAL の 1 か所に
    バッファを置き、どのホストアプリでも同じ恩恵を受けるようにした。
    - **二つのマトリクス**: アプリが書く「生」のマトリクス（kb_raw）と、
      ゲストが読む「可視」のマトリクス（従来の kmatrix）。keyscan
      （項目 32）、hal_keymatrix、器のポート 00H–0EH は従来どおり
      kmatrix を読む。halp8_set_matrix は生の行バイトと、セルごと
      （16 行 × 8 ビット）に生の値が最後に変わった実時刻を記録する。
    - **昇格規則**（kb_tick、セル単位。押す方向と離す方向で非対称）:
      - 押す方向（生が押下、可視が解放）: 待たずに、それを見た最初の
        駆動点で可視へ反映する。ホストからの押下エッジは意図した
        操作であり、ここでの待ちはそのままキーの重さになるため。
      - 離す方向（生が解放、可視が押下）: 次の両方を満たしたときだけ
        反映する。
        - 生の解放が KB_RELEASE_MS（10 ms）以上変わらずにいる。
          ホスト入力のばたつきは「解放＋押し直し」の組として現れる
          ので、10 ms 未満の組はここで吸収され、可視のセルは
          押されたままになる。
        - 可視の押下が KB_MIN_PRESS_MS（40 ms）以上続いている。短い
          本物のタップがゲストのポーリングの合間に落ちないようにする
          ため（従来どおり）。
      - **スナップショットの一貫性（引き連れ昇格）**【2026-11-23】:
        keyscan は押下エッジを、同じ可視スナップショットにある
        修飾キー（SHIFT／GRPH／CAPS／カナ）の状態で文字へ変換する。
        実機のマトリクスは一貫した 1 枚のスナップショットとして
        走査されるので、押下が保留中の解放を追い越してはならない
        （追い越すと「SHIFT を離してすぐ文字キー」が、まだ可視の
        古い SHIFT で変換される。GRPH なら文字が抑止される）。
        そこで kb_tick は 2 段で判定する。まずその駆動点で昇格する
        押下があるかを調べ、1 つでもあれば、可視の押下がすでに
        KB_MIN_PRESS_MS 以上続いている保留中の解放を、
        KB_RELEASE_MS の安定待ちを免除して同じ駆動点で（同じ可視
        スナップショットに）反映する。最小押下時間に達していない
        解放は免除されず、保留のまま残る（その間は古い状態が
        見える）。押下の昇格がない駆動点では上の規則のままなので、
        同じセルの「解放＋押し直し」は従来どおり吸収される（可視の
        セルは上がっていないので、押し直しは押下の昇格ではない）。
        代償: ばたつきの解放側の最中に**別のセル**の押下が届くと、
        その解放は通ってしまい、押し直しが新しい押下エッジになる。
    - **帰結**: 押下は次の駆動点で遅れなくゲストに届く。解放は
      10 ms 以上（短いタップでは可視の押下が 40 ms に達するまで）
      遅れる。どれほど短い押下でも、押下中に駆動点が回れば可視に
      なり、可視になってからは必ず 40 ms 以上見える（押下の開始と
      終了の両方が駆動点の合間に収まると、昇格する前に生の値が
      戻って何も起きない）。したがって解放で終わるばたつきは、
      見えなくなるのではなく 1 回の押下として見える。
      STOP、CAPS、カナのロックも同じバッファを通る（同じ規則）。
      文字キュー（halp8_push_key）はバッファを通らない。
    - **経緯**: 当初は押下・解放とも 20 ms の安定待ち
      （KB_DEBOUNCE_MS）を置く対称な規則だった。2026-11-22 の実機
      報告でキーが重く感じられたため、同日に上記の非対称な規則へ
      改めた。実際に起きていたばたつきはタッチの割り当ての入れ替わりと
      コントローラのスティックのドリフトで、どちらも解放側に出る。
    - **駆動点**: hal_poll（8 文ごとのゲートの後、keyscan の 64 文
      ゲートの手前で毎回）、hal_idle、hal_getkey。いずれも keyscan の
      直前で、インタプリタ側スレッド。生の状態と時刻はアプリの
      スレッドが書き、エンジンのスレッドが読むので、すべて既存の
      km_mu の下で扱う。昇格は kb_tick が呼ばれたときだけ進む
      （ゲストが音声リング待ちなどで止まっている間は進まない。
      時刻は実時間なので、再開した最初の呼び出しで追いつく）。
    - **時間の基準は実時間**: ゲストの CPU サイクルではなく壁時計
      （CLOCK_MONOTONIC、ミリ秒）。相手にしているのは人間の指と
      ホスト側入力機器の物理的な揺れで、ゲストの時間ではないため。
      4 MHz／8 MHz の選択（項目 33）にも依らない。
    - **実機との違い**: これは「キーボード側がチャタリングを除去して
      から見せる」という振る舞いをまとめてモデルしたもので、特定の
      チップやファームウェアのタイミングを再現したものではない。
      10 ms／40 ms は実機の測定値ではなく、入力機器のばたつきを
      吸収しつつ操作の遅れを感じさせない値として選んだ定数である。
    - **リセット**: halp8_session_reset は生・可視の両マトリクスを
      全セル解放、時刻を 0、ks_prev を全セル解放にそろえる（保留中の
      昇格もエッジも無い電源投入状態）。hal_init は両マトリクスと
      時刻だけを同じ初期状態に戻す（ks_prev 等のスキャナ状態には
      触れない。通常の起動ではセッションリセットが先に走る）。
    - **既存の基準への影響**: embed ハーネスのマトリクス押下

      pump を 10 回から 70 ms へ、リピート検査の解放待ちを 20 ms

    回帰ガード: tools/keybuffer_test.c（3 ms 周期のばたつきは最初の

35. **組み込み処理の仕事量課金（INP／PRINT／LINE）**（src/vessel.c
    vessel_charge、src/eval.c F_INP、src/print.c stmt_print、
    src/graph.c stmt_line）【2026-11-22 検証済み: 保持テスト PASS、
    回帰スイートは下記の基準再固定 2 件のみ差分】
    項目 6 の 1 文 2,000 サイクルは、文が何をするかに関係なく同じ量を
    課金する。実機 ROM では、関数の呼び出しと数値変換、1 文字ごとの
    テキスト出力、1 ピクセルごとの塗りに文の基本量よりずっと多くの
    仕事がかかるので、こうした処理の多いプログラムは器の上で速すぎた。
    そこで次の 3 つに、文の基本量とは別に「1 回あたりの仕事量」を
    課金する。
    - **実測**: MA2026A の *SELECT 画面（menu.BAS 1740〜1809 行）は
      キーマトリクスを INP(行) で直接読み（1 周あたり約 35 回）、毎周
      GOSUB *MFLG で LOCATE 74,1 + PRINT "      "（6 文字）+
      LINE (592,18)-(639,25),0,BF（48×8 ピクセルの塗り）を行う。
      実機（QUASI88、実 N88-BASIC ROM、4 MHz）ではカーソル下を
      1.0 秒押し続けると曲カーソルが 4 曲、上では 5 曲（折り返し込み）
      動く。1 周およそ 890,000 サイクル（毎秒約 4.5 周）。器は
      4 MHz で毎秒 13 曲（1 周約 308,000 サイクル）、8 MHz で毎秒
      33 曲だった。
    - **課金量**（いずれも 4 MHz のサイクル数。文の基本量に加算）:
      - INP(): 評価 1 回につき 12,000（INP_CHARGE_CYCLES。関数
        ディスパッチと引数・結果の数値変換）。
      - PRINT: 画面に出した 1 文字につき 1,500（PRINT_CHAR_CYCLES）。
        SPC／TAB／カンマ区切りが出す空白と改行も 1 文字と数え、
        1 文の合計を文の終わりに 1 回で課金する。PRINT USING も
        同じ。PRINT#（ファイル）と LPRINT は課金しない。エラーで
        中断した文は課金されない。数えるのは入力の 1 バイトごとで、
        表示幅ではない（文字列中の TAB は数桁の空白として表示
        されても 1 と数える）。較正上の簡略化として受け入れる
        （Astra レビュー L5、コード変更なし）。
      - LINE: 1 文につき 4,000 + 300 × ピクセル数（LINE_BASE_CYCLES /
        LINE_PIXEL_CYCLES）。ピクセル数は、直線は長い方の軸の長さ
        （描画ループの歩数）、B は 4 辺の合計（描画どおり角を 2 度
        数える）、BF は幅 × 高さ。いずれも描画と同じくビュー範囲で
        切り取ってから数える（画面外の座標で課金が膨らまない）。
        線種（破線）で打たない点も歩数には数える。

      *SELECT の 1 周では INP が 35 × 12,000 = 420,000、PRINT が
      6 × 1,500 = 9,000、LINE が 4,000 + 384 × 300 = 119,200 で、
      従来の約 308,000 と合わせて約 856,000（毎秒約 4.7 周）。
    - **較正値である**: 3 つの定数は ROM のルーチンを個別に測った
      値ではなく、*SELECT の 1 周が実機の実測（1.0 秒の保持で下 4 曲、
      上 5 曲）に合うように決めた値で、3 つの配分は推定。別の
      プログラムで INP／PRINT／LINE の比率が大きく違えば、個々の
      定数のずれが見える可能性がある。
    - **仕事であって時間ではない**: 項目 33 の区分で仕事に当たるので
      clk_mult を掛けない。8 MHz では同じ課金が半分の時間になる。
    - **進め方**: vessel_charge は PUMP_SLICE（16,667）以下の刻みで
      pump_advance を呼び、刻みごとに hal_poll を 1 回呼ぶ
      （vessel_burn のセクタ待ちと同じ規律。1 文の内側で時間が進む
      ので、ペーシングと停止要求の受け口が必要）。hal_poll は
      p8_bail で戻らないことがある。器がまだ動いていない間
      （pump_live が 0）と機械語の実行中は pump_advance が何も
      進めないので、課金も進まない。
    - **変えていないもの**: STMT_CYCLES、PUMP_SLICE、
      XDE_SECTOR_CYCLES などのペーシング定数、インタプリタの意味、
      描画と出力の結果。変わるのはエミュレーション時間の進み方だけ。
      他の組み込み（PEEK、PSET、CIRCLE、PAINT、PUT、LOCATE、文字列
      関数など）は従来どおり文の基本量だけで、実機より速いまま。

36. **テキスト合成の装飾ラッチ（反転・ブリンク・ライン）**（src/engine.c
    merge_text）【2026-11-22 検証済み: textmerge_test 拡張ケース
    全通過、回帰スイート PASSED（embed text / select_hold / restart
    含む）。アプリ側の反転描画とブリンク位相は P8Bridge（tf114〜）】
    ゲストのテキストイメージ（0xF3C8）の属性ペアを合成するとき、
    merge_text は色の半分（run_color／run_graph）とシークレット・反転
    だけを追っていて、出力する属性バイトは色とセミグラフィックだけ
    だった。反転は捨てられ、ブリンクと上線・下線はラッチすらされて
    いなかった。MA2026 の *SELECT 画面の曲カーソルは menu.BAS が書く
    属性 0xC6（bit3 が 0 の装飾バイトで、反転 0x04 とブリンク 0x02）
    なので、器ではカーソルが見えなかった。実機ではその行のラッチ済みの
    色で、点滅する反転バーになる。
    - **ラッチのモデル**（QUASI88 crtcdmac.cpp set_text_display と
      同じ）: ラッチはセルをまたぎ、行もまたいで持ち越す。色バイト
      （bit3 が 1）は色（0x80 G／0x40 R／0x20 B）とセミグラフィック
      （0x10）だけを置き換え、装飾は残す。装飾バイト（bit3 が 0）は
      装飾を**すべて**置き換え、色とセミグラフィックは残す。装飾
      バイトをまたいで残る装飾はない（ビットのない装飾バイトは全部を
      消す）。
    - **ビットの対応**（ゲストの装飾バイト → src/screen.c のホスト
      属性形式）:
      - 0x01 シークレット → 従来どおりセルのコードを 0 にして隠す。
      - 0x02 ブリンク → 0x02。
      - 0x04 反転 → 0x04。
      - 0x20 下線 → 0x08。
      - 0x10 上線 → 0x08。ホスト形式にはラインのビットが 1 つしか
        ないので、上線は下線と同じ表示になる（上線と下線の区別、
        両方同時の指定は失われる）。
      色は bit7〜5、セミグラフィックは 0x10 のまま。
    - **bit0（表示）は立てない**: ホスト形式の bit0 は「表示」だが、
      merge_text はこれまでもイメージ由来のセルで bit0 を立てて
      おらず（0xC0、0x90、0xA0 など）、シークレットはコードを消す
      ことで表していた。textmerge_test の既存の期待値と
      run_regress.sh の embedsel（合成属性に `a0a0` があること）が
      この形に依存しているので、そのままにした。bit0 を見て隠す
      レンダラは、合成されたセルを隠してしまう。
    - **ブリンクの位相はレンダラの仕事**: エンジンはブリンクの
      **ビット**を出すだけで、セルを消したり隠したりしない。点滅の
      周期と位相はレンダラが決める。こうしてあるのでテキストの
      ダンプは位相に依存しない。
    - **インタプリタのセル**: 属性ペアが支配するインタプリタ側の
      セルは、同じ合成属性をそのまま受け取るので、反転・ブリンク・
      ラインも一緒に付く。置き換えの条件は「反転があるとき」から
      「装飾（反転・ブリンク・ライン）のどれかがあるとき」に広げた
      （ブリンクだけ、ラインだけの装飾バイトもインタプリタのセルに
      届く）。色を言い直すだけのペアがインタプリタの属性を変えない
      点は従来どおり。
    - **変えていないもの**: 幅 40 の経路（halp8 の属性をそのまま
      返す）、ペーシング、src/vessel.c、項目 35 の課金。アプリ側の
      反転の塗りとブリンクの位相は別作業。
    - **既存の基準への影響（未確認）**: 合成属性のダンプ
      （embed_test の「ATTRS (merged)」）で、装飾の付いたセルの値が
      変わる（例: シアンの反転＋ブリンクは a0 → a6）。embedsel の
      `a0a0` の検査は、装飾のないシアンのセルが 2 つ並んで残って
